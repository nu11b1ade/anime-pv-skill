# 持续维护与发布

## 日常变更

1. 明确问题属于工作流、协议、工程还是文档；阅读架构约定。
2. 修改最小相关范围；需要时增加离线行为测试。
3. 执行 CONTRIBUTING.md 的结构检查和 unittest；等待 CI 的平台结果。
4. 更新 CHANGELOG 的 Unreleased；能力边界变化同步运行时 references。
5. 记录未验证部分。不要仅因 CI 通过就承诺接口可用性、画质或真实重渲染能力。

## 协议维护

官方文档入口集中在技能的 references/image-backends.md。用户报告接口变化、模型不支持或响应结构变化时，按对应平台核对，不需要每次任务读取所有文档。记录核查日期及能力边界；在测试中加入去除秘密的最小响应或构造响应。

检查请求方法、鉴权、端点拼接、编辑/参考图输入、mask、异步状态、结果字段与平台参数。任何“兼容”服务都只承诺已经实现的协议形状，不承诺所有供应商和模型。

新增真实验证记录应包含：日期、OS/Python、协议、模型、地区、操作、结果和限制；不含 key、账户信息或签名 URL。初始验证记录保留历史事实，后续验证另记日期，不覆盖旧结论冒充从前已通过。

## 依赖与兼容性

根目录 pyproject.toml/uv.lock 固定维护测试环境。运行时脚本可独立通过 PEP 723 安装所需依赖；两处范围应一致。升级依赖后重新运行跨平台 CI；更改 Python 最低版本时同步脚本头、pyproject 与 CI matrix。

默认 CI 不调用生图 API，不安装本地模型，不要求图形桌面或 ffmpeg。媒体和实际渲染验证按具体项目或修改范围单独执行。测试平台、Python 版本和真实服务验证是三个不同维度。

## 发布检查

尚未创建正式版本标签。准备发布时：

- 检查 main 的 CI、未完成变更及已知限制，整理 CHANGELOG。
- 检查运行时链接、模板、配置字段、恢复行为和依赖记录。
- 对有行为不兼容的修改写清迁移方法；尤其避免旧任务被当成新任务重新提交。
- 交付技能时打包完整 anime-pv 目录，排除 .env、缓存和 __pycache__；仓库维护文档不需要进入技能安装包。
- 由维护者选定版本号、许可证与发布范围后创建标签/Release。首次公开仓库本身不等于已经正式发布版本。

建议版本含义：修正为 patch、向后兼容能力为 minor、不兼容的项目/任务状态或配置变化为 major；0.x 阶段也明确记录不兼容变化。

## 新维护会话的入口

先读 README → 本文件 → ARCHITECTURE，随后检查 git status、最近提交、CHANGELOG 与 ROADMAP，按改动范围读源码。以文件和可执行检查为准，不依赖创建仓库时的私人会话。若只修改技能工作流，避免顺带更换渲染工具或生图后端。
