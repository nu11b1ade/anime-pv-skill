# 项目状态与阶段交接

项目目录承载完整状态，`HANDOFF.md` 是唯一恢复入口。入口保持短小；链接使用项目内相对路径，方便迁移。推荐按用途放置 inputs、assets、design、previews、render、deliverables、state，不强迫特定工程内部布局。

## 写入与批准

每个批准项至少包含：稳定 ID、决定内容、状态（proposed / approved / invalidated）、用户确认的时间或消息摘要、适用范围、所依赖的决定 ID，以及证据文件版本/哈希。模型验证通过不等于用户批准。更新入口前保存旧版到 `state/history/`；素材、demo、工程使用不同版本名，不覆盖已批准证据。

使用 [HANDOFF 模板](../assets/HANDOFF.template.md) 建立入口。完成阶段后：

1. 给用户展示可审阅成果、关键差异和未验证项。
2. 收到批准后记录真实批准范围，不把局部认可扩大为全阶段认可。
3. 保存决定和证据版本，更新入口中当前阶段、下一阶段、验证状态及下一步。
4. 默认停下，给出恢复提示：“在可访问完整项目目录的新窗口中，读取 `<项目>/HANDOFF.md`，核对批准项和文件版本后继续下一阶段。”用户已明确要求当前窗口继续时照做。

中途暂停也更新入口，但保持阶段未批准。不得为产生交接而伪造共识。

## 新窗口恢复检查

先读入口，再只读当前任务相关资料。核对模式、输出规格、音频政策、当前版本、已批准证据存在且哈希未变、生图途径/后端已获选择、运行命令与依赖是否可用。配置来源只记录位置、协议、模型等非敏感信息，不记录 key 或带签名参数的 URL。

简短说明恢复到哪一步、哪些项目仍待验证，然后继续授权范围内的工作。缺文件或证据变更只阻止依赖它的任务；不要重新设计未受影响的批准内容。换机器后工具和字体需要重检，源机器“通过”不自动继承。

## 回改

先说明变更影响的素材、镜头和批准 ID。保留原版本，只将直接及传递依赖项标为 invalidated；无关项保持 approved。新证据完成后只重新确认必要部分，并更新当前版本指针。

## 搬迁与打包

创建 `state/package-files.txt`，逐行列出重渲染所需的项目内文件：入口、决定、批准样片、输入、素材、字体（可分发时）、渲染代码、锁文件和运行说明等。运行：

```sh
uv run <skill>/scripts/project.py pack <项目> --manifest state/package-files.txt --output <项目外>/pv-project.zip
```

脚本只复制明确列出的文件，拒绝越界、符号链接和常见凭证文件名；模型仍需检查清单内容，不能把文件名检查当作完整的秘密扫描。不打包 .env、任务缓存、环境目录和不必要的渲染缓存。目标机解压后从入口恢复，不依赖旧机器绝对路径。
