# 三方中转生图：选择与使用建议

适用于用户授权API生图后的后端选型。三方中转是实际服务提供者；`openai`等协议名表示请求形状，`gpt-image-2`等模型名称可能是路由别名，不证明调用了官方同名模型，也不证明透传了所有参数。

## 作为完整PV生图路径的基本能力

| 能力 | 最小验证 | 不满足时的影响 |
|---|---|---|
| 文生图与构图指令 | 代表性主视觉，角色位置、留白、画风和道具符合要求 | 无法稳定探索镜头 |
| 单图参考与身份保持 | 同一角色换姿势/背景，保留发型、服装和关键标志 | 角色容易跨镜头漂移 |
| 至少两张参考图 | 角色图＋道具/服装/构图图，明确各图作用 | 只能依靠文字描述重构，不能支撑完整多源创作 |
| 指令编辑 | 在原图改色或去物，主体、构图基本保持 | 回改容易整张重做 |
| 可用原图与可靠交付 | 返回可解码图片、可保存本地；明确超时、失败、任务查询/账单核查方式 | 会卡在下载或不确定提交，无法安全续作 |

基本能力按当前端点、模型、协议组合测试，不按厂商一刀切；授权多个途径时可以由不同途径分别覆盖。可用尺寸应足以覆盖目标镜头的有效细节和裁切空间；没有统一必须4K的门槛。二次元风格与手部、文字能力也应以项目样片判断。

## 需要按项目补测的能力

- 分层角色：真实alpha背景、发丝与半透明边缘，或明确可用的抠图流程。不能用画出的棋盘格冒充透明。
- 精确复刻：局部编辑保护、原图尺寸保持、必要时mask。即使有mask字段，也不保证遮罩外像素不变。
- 多轮修改：将一轮输出作为后续输入，检查服装、脸和道具是否累积漂移；每轮保留版本。
- 批量制作：多张输出、并发/配额与失败隔离；没有n参数可以逐张调用，不属于画质不足。
- 中文与特定文字：需要画进图内时实测；精确排版更适合独立文字层。

尺寸不精确、alpha最高254等机械差异不自动意味着创作不可用。实测中内置与中转都出现过这些情况；应检验最终画布和合成观感。

## 使用中转的具体建议

1. 确认它实际支持所选协议的图片生成和编辑操作。OpenAI兼容路径必须支持`/images/generations`、multipart `/images/edits`、重复`image[]`的多文件输入；只支持聊天或只支持网页上传不够。其他协议按对应适配器传图。
2. 要求服务方说明模型路由、参数支持、参考图张数/大小、输出原图方式与超时行为。参数不支持应明确报错或告知；不要把接受参数视为执行参数。不要为了适配中转无证据地更换协议或字段。
3. 首次用项目代表性任务验证单参考、多参考和编辑，保存提示词、实际尺寸、产物与限制。
4. 参考图优先用少量清晰原图，明确每张的用途。脚本会给OpenAI上传分配唯一文件名；没有证据时不压缩输入、不丢弃额外参考图，也不转成“仅文字描述”冒充多图能力。
5. 结果先落盘、再验收。精确尺寸优先由参数表达，同时可用提示词表明构图；若仍不符，按实际输出合成，不不断付费重试同样提示词。主体身份或构图不合格才需要有针对性的再生成。
6. POST超时、断线、无效JSON可能已经产生任务或计费。先保存unknown和诊断、核查服务后台；不要自动换端点重发。若服务没有查询能力，应如实报告限制。
7. 参考图和提示词会经过中转服务；选择用户信任、素材使用范围允许的服务。凭证只放本地.env，不放请求文件、交接、公开报告或仓库。

已知某个中转的表现不能推广到其他中转，也不能当作官方API验证结果。模型名称相同、尺寸相似、画风相似都不足以识别上游实现。协议适配范围与官方文档来源见 [生图途径与后端](image-backends.md)，这些来源用于核查接口范围，不是第三方中转质量背书。
